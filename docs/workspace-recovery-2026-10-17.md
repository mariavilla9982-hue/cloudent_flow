# Workspace recovery — 2026-10-17

The login migration reached an empty target database. This recovery restored the application schema and the records from the supplied database backup into `iubzjfidmxfjvvonusos`, preserving identifiers, account bindings, terminal job states and hidden history.

Recovered: 45 public tables, 215 video records, 190 schedules (18 future), 4 platform accounts, 128 production jobs, 43 Face Swap jobs and 11,613 metric snapshots. All 190 schedules retain an explicit account. The disconnected Instagram account remains disconnected. Auth sessions, password hashes, temporary OAuth challenges, local-password fallback credentials and old cron execution logs were not imported. The existing administrator login remains intact; the disabled legacy member identity was recreated through Auth Admin solely to preserve foreign keys and remains disabled in app membership.

The original Julia and Sahry image bytes were recovered independently of the database dump, uploaded to the private production bucket and verified using their original SHA-256 hashes. Both signed downloads returned HTTP 200 with matching content. No other physical Storage objects are claimed restored; the database dump contains references and metadata, not their file bytes.

Database rules were validated in isolated PostgreSQL and applied through the connected migration interface in bounded transactions. The numbered schema migrations in this commit are the exact successful target migration records. Failed transport attempts and the rolled-back timestamp collision did not become migrations. Original foreign keys, policies, account binding triggers, indexes and sequence positions were restored. X authorization uses the new project's native Auth membership; the retired local-password bridge was not reintroduced. Direct anon execution of privileged public functions remains revoked.

The new project cannot use the old encrypted Vault values. Direct access to the old project is denied to the current connection. RunningHub, Backblaze and social account credentials require transfer or reconfiguration; old encrypted values are preserved in the original backup. A new worker encryption key was generated within Vault, never in source code. Restored accounts requiring credentials are labelled for reconnection. New Motion uploads reject missing provider credentials before storage writes or paid execution. Workflows, node mappings, GPU policy and existing task IDs were not changed.

Read/status APIs and the existing Motion/production workers were deployed in the new project. No periodic jobs were enabled and no real generation, publication or retry was started. Production history was already hidden in the backup and was not unhidden or replayed.

The frontend now tolerates a cold backend during boot instead of giving up after four seconds. Tests covered Auth isolation, X permissions, stale account responses, PostgreSQL schema, model selection with transaction rollback, source/target row counts, signed model downloads and the Motion credential gate. End-to-end generation/publication remains blocked by provider credentials and missing physical media, not declared successful.
